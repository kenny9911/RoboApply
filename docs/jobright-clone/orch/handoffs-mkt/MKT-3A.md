## Items

### 1. [P0] Monthly quota read from every RapidAPI response and stored in AppConfig (JI-1): done

- **Capture.** `raRapidApiJobs.ts` and `raFantasticJobs.ts` export `setQuotaListener(listener | null)` and call it once per upstream response (200 and other statuses, 429, 401, 403; both attempts of a retried 429; never for a cache hit, never for a network error). The observation is built by one pure function in `raExternalJobTypes.ts`, `quotaObservationFrom(provider, response, bodyText, at)`: `{ provider, status, requestsLimit, requestsRemaining, resetSeconds, jobsLimit, jobsRemaining, plan, reason, at }`. `plan` is the token after "current plan," in a 429 body; `reason` (`'monthly_quota' | 'not_subscribed' | null`) is one field more than the item lists, so the 403 kinds can be told apart without passing the body on. A header that is not a non-negative number is `null`. A listener that throws is swallowed. The key is never part of it.
- **`quota.ts`** (new) keeps the latest snapshot per provider, derives the state, computes `resetAt = at + resetSeconds` and `lastCallCost` (drop in `requestsRemaining` since the previous reading when that reading is under 60 s old), and stores the whole map in AppConfig `jobs.providerQuota.v1` through MKT-1C's `serializeProviderQuota`: at once on a state change, otherwise at most once every 60 s per provider.
- **The write is conditional (review fix).** The row is read and merged (newest reading per provider wins), then written only if it still holds the text that was read (`updateMany where { key, value: <as read> }`; `create` when there was no row, a unique violation meaning "another process created it"). On a miss the row is read, merged and written again, at most `QUOTA_WRITE_ATTEMPTS` (3) times, then a warning. A write that would change nothing is skipped.
- **A reading that closes or reopens a provider is stored before a person's request ends (review fix).** The registered listener (`quotaListener`) answers with the pending write for such a reading; a client serving a person's own search waits for it, at most `QUOTA_LISTENER_WAIT_MS` (500 ms, `settleQuotaListener` in `raExternalJobTypes.ts`). An ingest call never waits (its tick awaits the writes); any other reading is stored in the background as before.
- **`hydrateProviderQuota(db)`** loads the stored map (newest reading wins, never throws). Called at the start of `runJobsPlan`, `runJobsIngest`, the `ingest.query` worker and `ingestForProfile`. A snapshot whose `resetAt` has passed reads as state `unknown` with `requestsRemaining`, `jobsRemaining` and `lastCallCost` null; limit and plan name are kept.
- **Read API:** `quotaSnapshot(provider, now)`, `providerQuotaSnapshots(now)`, `quotaAllows(provider, 'ingest' | 'interactive', now, env)`, `quotaRetryAt(provider, now, env)`, `quotaParkUntil(provider, now, env)`. Ingest is refused in a closed state (exhausted, not_subscribed, unauthorized) and while `requestsRemaining <= max(1, ceil(requestsLimit × INGEST_QUOTA_RESERVE_SHARE))`; a person's own search only in a closed state or at 0. No snapshot: both allowed.
- **How long a reading blocks (review fix).** A used-up plan, or one at its reserve: until the reset the provider stated (one hour when it stated none). A refused key or a missing subscription (401, any 403): one hour after that answer (`QUOTA_RETRY_MS`), whatever reset its headers carry. The reset says when the quota refills, not when a key or a subscription is put right; one call an hour asks again, as the clients' breakers do. `resetAt` stays in the snapshot for display.
- **Registration.** Importing `quota.ts` registers listener and gate with both clients. `ingest/index.ts`, `ingest/cron.ts`, `ingest/run.ts`, `ingest/pipeline.ts` and `adapters/rapidApi.ts` import it; `app.ts` imports `cron/handlers.ts`, which imports `ingest/cron.js`, so every deployment has it at process start (checked).

Departures from the item text, both on the contract's side:
- A 2xx whose own headers say `requestsRemaining: 0` or `jobsRemaining: 0` is state `exhausted`, not `ok`. The item says "a 2xx -> ok"; MKT-1C's contract defines `ok` as "served and quota remains". This is what makes a per-job plan (Active Jobs DB: 250 postings a month) stop before its next call is wasted on a 429.
- A plan name is carried to later readings only while the stated request limit is unchanged ("BASIC" from an old 429 must not stand next to a 20,000-request limit after an upgrade: D3).

Tests: `quota.test.ts` (39) covers every ACCEPT line: the 429 with remaining 0 and a reset in 16.9 days (state, plan BASIC, resetAt, the stored row, refused until that instant and allowed from it); 9,773 of 10,000 with `lastCallCost` 2; 403 not subscribed, 401, another 403; a refusal WITH quota headers blocks one hour, in this and in a second process; reserve arithmetic; the 60-second debounce per provider and the immediate write on a state change; a second process that only hydrates gives the same answers with `fetch` never called; an expired snapshot; two processes merging; two processes writing at the same moment (the interleaved write is detected, re-read and merged); two processes that both find no row; a row that keeps changing (three tries, a warning, no throw); an older reading never written over a newer stored one; a failing database never fails the caller; the listener's answer per kind of reading; `settleQuotaListener`; a person's search returning only once the "used up" reading is stored while an ingest call does not wait; the key in no snapshot, stored row or log line (both real clients wired, mocked `fetch`). Client tests: listener values for 200 / 429 / 403 / 401, not for a cache hit, a throwing listener, the 500 ms bound with a write that never finishes.

### 2. [P0] One budget per provider (JI-1, JC-6 preparation; C13): done

- **`config.ts`:** `effectiveDailyLimit(provider, market, env, now)`. intl: the smaller of the operator's bound and the quota's daily cap; with neither, the old defaults (activejobs 300, jsearch 200). The cap (`quotaDailyCap`) is `floor((requestsRemaining − reserve) / max(1, daysToReset))` REQUESTS a day, **divided by what one call costs once the headers have shown it** (`lastCallCost`; unknown or under 1 counts as 1) (review fix): 9,773 of 10,000 with 17 days to go is 545 calls a day, and 272 once a call is known to take two requests. cn: `INGEST_<PROVIDER>_CN_DAILY_CALLS` (default 0) under the same cap. `RA_ONBOARDING_<PROVIDER>_DAILY_BUDGET` (LinkedIn's old name carries `_JOBS`) is read as a deprecated alias while the `INGEST_` name is unset, logged once per name. `dailyCallLimit(provider)` is still the operator's bound for the admin Limits page. Also `quotaReserve`, `quotaReserveShare`, `cursorTickShare`, `quotaRecheckMs`.
- **`pipeline.ts` `runIngestQuery`:** a metered adapter whose quota refuses ingest has every due query of the provider parked with `buildDeferProviderSql` and the result is the new status `'quota'`. **Parked until `quotaParkUntil`: the time the reading stops blocking, at most 24 hours ahead (`QUOTA_PARK_MAX_MS`) (review fix).** A plan used up for weeks is looked at once a day (one lease, one statement, no provider call) and its queries run within a day of the plan reopening, whichever process learns of it; nothing has to release them. Reservation and usage rows use `usageKey(provider, ctx.market)` and `effectiveDailyLimit`; enablement uses `adapterEnabledFor(adapter, ctx.market)`. `reserveProviderCall` and `recordProviderUsage` moved to `quota.ts` and are re-exported from `pipeline.ts` (same SQL, no snapshot changed). `PipelineContext.env` is new (optional).
- **A reading that has stopped blocking no longer sets the day's limit (found while fixing the review's second finding).** After the hour of a refusal, or the `INGEST_QUOTA_RECHECK_HOURS` window of a used-up plan, `quotaAllows` opened but the day's cap computed from the old "0 left" was still 0, so the reservation refused the very call that would re-read the plan and pushed the provider to the next UTC day. The budget now gets no reading in that state (`budgetReading` in `quota.ts`) and falls back to the operator's bound or the default; the first response replaces it.
- **`run.ts`:** `'quota'` is listed under `budgetStops` and drops the provider for the tick like `'budget'`. `adapterRunsInTick(adapter, market, now, env)` = enabled, or metered and stopped only by its quota: such a provider is leased once so its queries can be parked in one statement (a provider that is simply off is still not leased).
- **Clients:** the in-process daily counters, their env reads and warn-once state are deleted. Each client exports `setCallGate(gate | null)`; `gate(provider, purpose, { probe? })` is asked before every upstream call (again before the one retry after a per-second 429) and, with `probe`, by `isJSearchEnabled` / `isFantasticJobsEnabled`. No gate, or a gate that throws, allows. `ProviderSearchOptions.reservedByIngest` is new; the ingest adapter passes `true`. LRU caches, breakers and kill switches are unchanged.
- **The gate (`quota.ts` `providerCallGate`):** an ingest call gets the quota answer only (the pipeline already counted it). Any other call is a person's search in the brand of the request: refused for market cn unless the provider is Active Jobs DB and its mainland bound is above 0 (JSearch never: strategy M-6, 1.6); refused when the operator's daily bound is exactly 0; refused by the quota at 0 or a closed state; otherwise counted once in today's `RAProviderUsage` row under `usageKey(provider, market)`.
- **A source's own `isEnabled()` answers for its own market (review fix).** The RapidAPI ingest adapter asks the clients inside `answerForMarket('intl', …)` (new, `quota.ts`): the gate answers that probe as an international call, whatever brand the request has. An admin on the GoApply host who lists every site's sources no longer reads RoboApply's JSearch and Active Jobs DB as off. The adapter's `isEnabled()` is "client usable AND `quotaAllows(id, 'ingest')`", so an adapter down to its reserve reports itself off and the planner plans nothing for it.
- **Cursor share (strategy 1.3, C12):** `runIngestTick` tracks milliseconds per cursor provider. A cursor source that still reports more rows steps aside once its share (`INGEST_CURSOR_TICK_SHARE`, default 0.4) is used; its query was finished with `nextRunAt = now`. Each fetch is handed `min(what is left of the tick, what is left of its share)` as `SourceFetchContext.budgetMs`; a second query of a source whose share is used is handed back (`nextRunAt = now`) instead of being run with no time. **When a lease finds nothing else due and the tick has time left, the sources that stepped aside get another share (review fix)**: a tick with one cursor source and no demand gives it the whole tick, a share at a time, as before the market wave; with demand due the first share and the demand's precedence are unchanged. `INGEST_CURSOR_TICK_SHARE` is clamped to 0.05..1. `TickOptions.clock` is new (tests).
- **Queries leased with the last one a tick had time for are handed back** (`nextRunAt = now`) instead of being left to their 15-minute lease, except those a spent day or a quota stop already moved. Added with the previous point: a cursor source that uses the tick to its end makes "out of time" the usual way a tick stops, and a demand query leased in that last batch would otherwise have waited a tick longer.
- **Refresh by country:** `const refreshInput = { origin, demandScore, consecutiveEmpty, country: query.params.country ?? null }; nextRunDelayMs(refreshInput)`, a variable as the contract says.

Departure from the item's ACCEPT wording: "defers its due queries to the reset time" is now "parks them until the quota stops blocking, a day at a time". With the literal rule the queries stayed parked at the old reset after the owner bought a plan (the review's second finding); the reviewer offered this form as the fix.

## Known gaps

1. **Never run against Postgres or RapidAPI.** The new statements (the RACompany lookup, the gate's usage upsert, the conditional AppConfig `updateMany` / `create`) were only exercised on the fake. The conditional write compares the row's whole text (about 400 bytes per provider), which Postgres does with a plain equality on the row found by its unique key.
2. **The interactive call count is fire-and-forget.** The gate must answer synchronously, so the usage row is written in the background (queued before the upstream call starts; ticks await the queue). A serverless function frozen right after its response can lose one count. The monthly truth is the provider's own header, read on every response; a reading that closes or reopens a provider is now waited for.
3. **Interactive calls are counted, not capped per day.** The gate cannot read the day's row synchronously. Ingest yields to them (same row, the reserve); they stop at the plan's quota.
4. **The stored reading can trail memory by up to 60 s** of calls for an unchanged state (the debounce the item asks for). A cold process corrects itself with its first response.
5. **A used-up plan is not re-read before its stated reset** unless `INGEST_QUOTA_RECHECK_HOURS` is set (Owner 1). The ACCEPT line "false until that instant" is why the default is 0. With it set, the re-read costs one call per window.
6. **After a plan reopens, parked ingest queries can wait up to 24 hours** (the park cap). A reopening is not pushed to the parked rows; they come due on their own.
7. **`lastCallCost` is a header delta**, so calls made by another process inside the same minute inflate it, and the first response of a process has none. The day's limit can therefore read low for a moment (545 requests / an inflated cost), and a reservation refused in that moment ends the provider's ingest day early. It errs toward spending less: what is not spent stays in the plan and raises the next day's cap. With no cost known the limit is the undivided 545.
8. **The retry after a per-second 429 inside an ingest call is not counted** in `RAProviderUsage` (the pipeline reserved one call; the gate does not count ingest). At most one extra call per query, visible in the header count.
9. **Three writers colliding three times in a row** leave a reading unstored (a warning is logged); it stays in the process's memory and is written with the next reading that is due.
10. **A page-stated job-board host is skipped as an employer domain** (item 5): a deliberate departure from the item's wording, flagged for MKT-3C.
