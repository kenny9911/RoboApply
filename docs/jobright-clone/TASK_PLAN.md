## 2. Rules every work package follows

### 2.1 Ownership and collisions
1. **Exclusive ownership.** A WP edits only the paths in its `owns` list. Paths ending in `/` mean the whole directory. Within one wave no two parallel WPs own the same path or a parent/child of it (Appendix A is checked for this by script).
2. **Need a change elsewhere?** Do not edit. Put it in the handoff under "Requests" (`for <WP-ID or INT>`). Hot files (§4.0) are touched only by FND and INT, except where a later WP is explicitly granted one (e.g. WP-75 owns `server/src/app.ts` in Wave 5).
3. **Interface-first.** FND-5/FND-6a/FND-6b/FND-7 create every cross-area seam (contracts, `index.ts` public surfaces, stub components, stub hooks, `lib/api` wrappers). A WP may call a same-wave sibling **only through a seam that already exists**; stubs return `501 not_implemented` (server) or render `null` (client) until the owner fills them. A producer that a **later** wave extends must ship the extension point named in its acceptance (e.g. WP-21a `registerRail()`, WP-39a `registerDeliveryChannel()`), because its files have no owner after its wave.
4. **Cross-area imports** go through `server/src/features/<area>/index.ts` or `components/features/<area>/index.ts` only.
5. **Typed Prisma only** in new code (`prisma as any` is banned in `server/src/features/**` and `server/src/platform/**`; the boundary check fails on it).
6. **Schema: WPs never edit `.prisma` files and never run `db push`.** A WP that needs a field, index or relation FND-1b missed lists it under "Schema requests" in its handoff. At the next wave gate the orchestrator runs **SCHEMA-n** (§4.0): applies the wave's requests, `prisma validate`, `db:generate`, the additive-diff checks, and asks the owner to confirm an additive push to the clone Neon branch **before the next wave starts**. Until then the WP codes against the field behind a narrow typed adapter and marks the dependent test `it.todo` with the request id (the only allowed `todo`). WP-90 only reconciles.
7. **No new runtime dependencies** outside FND-2a (root) and WP-55b (the `extension/` package's own lockfile). Need one? Handoff request.
8. **Deletion rule.** A WP never deletes a module that a file it does not own still imports. "Retire" inside a wave means: stop calling it, mark it `@deprecated` with the replacement, and list it for WP-75 (Wave 5), which deletes it after a zero-importer grep. Routes mounted from a hot file (`server/src/roboapply/v2/routes/index.ts`, `server/src/app.ts`) are unmounted only by WP-75 or WP-93.
9. **The legacy V2 client is frozen.** `lib/api/v2/{_real,raV2Api,index,types}.ts` and `lib/stub/raV2.stub.ts` (58 importers) are hot. New calls go only through the area wrappers in `lib/api/<area>.ts`; a WP that changes an existing V2 endpoint keeps its response backward compatible (additive) or moves every caller it owns to the new wrapper. WP-75 deletes the dead V2 slices.

### 2.2 Copy, honesty and product rules (checked in review)
- **D1:** allowed verbs are Prepare, Tailor, Write, Fill this form, Open application, Apply on company site, I applied. Nothing clicks a submit control. No server-side apply. No copy that implies we submit, greet or send. `Open application` and `Apply on company site` both move the job to Applied at once with an inline Undo (R-19). The extension never watches or detects submits; "submitted" is only ever what the user tells us.
- **D3:** every non-user number is a `Sourced<T>` on the wire (`{value, source, sampleSize?, asOf, method?, url?}`) and renders through `SourceNote`. Unknown renders `—` / "Not listed" / "未披露", never 0. **One sample rule:** aggregates (pay medians included) need `sampleSize ≥ MIN_SAMPLE = 20` rows in one currency and period, and show N ("Pay listed on {X} of {N} posts"); the constant lives in `components/features/common/SourceNote.tsx` and its server twin `server/src/platform/http.ts`. **Every aggregate and public count** filters `visibility='public' AND isCanonical AND archivedAt IS NULL AND market = brand.market` (users' imported jobs never count). AI output is labelled as AI. People shown are real records from a named source.
- **AI prompts never contain** photo, 籍贯, 政治面貌, gender, birth date, family members or EEO answers; renderers place them in documents after the model runs (`profileSnapshotForLlm()` from WP-19 is the only context builder).
- **GoApply AI consent:** every LLM call made for a user goes through `aiAllowed(user)` (`server/src/platform/consent/aiAllowed.ts`, FND-2a). On GoApply it is true only with an `ai_resume_parsing` grant; on RoboApply always true. When false, MATCH falls back to the deterministic pre-score labelled "Quick estimate", and COP, RES, CL, AGENT and EXT hide their AI actions. Each such WP has a test asserting **zero `LLMService` calls** with consent off.
- **Plain language** per rulings section B; the fit line "This is not your chance of getting hired." under every score; tier words Great fit / Good fit / Possible / Unlikely; no "match", "ATS", "insider", "hidden jobs", "auto-apply" in UI copy.
- **Design:** Clarity tokens only (`var(--*)`, `--fs-*`, spacing scale); CSS Modules colocated in `components/features/<area>/`; primitives from `components/v3/primitives/`; light + dark × both brands; 375 px and 1280 px; 44 px touch targets; every feature works on mobile.
- **Brand neutrality:** never write "RoboApply"/"GoApply" in bundles (use `%BRAND%`/`%OTHER_BRAND%`); server code uses `getCurrentBrand().name`. **Source names are allowed:** `RoboHire` and `GoHire` render through ICU params (`{sourceName}`) filled from data, or literally under `legal.*`, `jobsCn.source*` and `people.source*` (D3 requires naming real sources).
- **AI labels on GoApply:** every block of AI output renders `AiGeneratedBadge` when `brand.market==='cn'` (WP-18, 22, 36a, 37, 43, 51, 59, 65, 66 acceptance).
- **Popups:** any unprompted modal/prompt goes through `lib/ui/popupGate.ts` (one per page view, 24 h budget).
- **Messages:** promotional nudges (PRODUCT §7.3 rows 5, 6, 10) sit under one "Tips and reminders" preference, default **off** for EEA/UK/CH/CA visitors and GoApply, on elsewhere; one-click unsubscribe on every send.

### 2.3 i18n during the waves
- Write English strings to `i18n/staging/<namespace>.en.json` (`{"<namespace>": {...}}`), one namespace per WP (Appendix A `namespace`). GoApply WPs may add `<namespace>.zh.json` (R-22). Extension strings go to `i18n/staging/extension*.en.json`.
- **Server email strings** go to `server/src/i18n/email/staging/<area>.en.json` (inside `server/src`, so `rootDir` and Vercel's `includeFiles: server/**` both cover them). FND-3 creates the files and the loader in `server/src/platform/email/i18n.ts` merges them over `server/src/i18n/email/en.json`; the merge script reads them from there.
- Never edit `i18n/messages/*.json`. Need an existing key changed or removed? Add the new key in your namespace, switch your call sites, and list the old key in your handoff (INT removes it).
- The runtime merges staging English over `en.json`, so every locale renders English for new keys until INT translates.

### 2.4 Worktrees and verification (every WP, in this order)
**One worktree per WP.** The orchestrator cuts each WP from the wave tag: `git -C /Users/kenny/code/RoboApply/.claude/worktrees/jobright-clone worktree add ../wp-<id> -b wp/<id> jobright-w<n>` (a WP that depends on a same-wave WP is cut after that WP merges), symlinks `node_modules` (root, and `server/node_modules` when present) from the clone worktree, copies `.env`/`.env.local`, and runs `npm run db:generate`. The agent works and verifies **only** in its own worktree, so siblings' half-written files never break its gates.
1. Smallest relevant tests: `npx vitest run <your test paths>`.
2. `npm run typecheck:server` (server changes) and `npm run typecheck:web` (frontend changes; script added by FND-7).
3. `npm run check` (design, copy incl. staging, LLM costs, API boundary, extension no-submit, zh variants).
4. `npm test` (full suite).
Feature agents **do not** run `npm run build`, `prisma db push`, dev servers, or browsers. UI behaviour is proven with Testing Library + jsdom; INT does browser verification. The orchestrator may run one dev server per wave for spot checks, from the clone worktree.

### 2.5 Done, handoff and merges
- **Definition of done:** acceptance criteria met; tests added (pure logic ≥90% branch coverage where ARCH §10.3 says so; every route ≥1 test incl. auth and `feature_disabled`); all four verification steps green in the WP's worktree; no TODOs that hide missing behaviour; no new hard-coded brand names; no fabricated data.
- **Handoff = the agent's final message**, in this shape: `WP-ID` · status · files created/modified/deleted · tests run (commands + pass counts) · Requests (by target WP/INT) · Schema requests · i18n keys added/obsoleted · env vars introduced · known gaps.
- **Agents never commit or push.** The orchestrator verifies the seam, commits the WP's explicit paths on `wp/<id>` (`feat(<area>): <summary> (WP-xx)` ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`), checks that the diff touches only owned paths, and merges the WP branches into `feat/jobright-clone` in dependency order.
