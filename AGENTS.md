# RoboApply repository guide

New to the project? The engineering handbook in `docs/handbook/` (start at
`docs/handbook/README.md`) covers the product, architecture, data model, AI
stack, features, deployment and current status. This file is the short version.

## Architecture

- The repository root is a Next.js 16 App Router frontend (`app/`, `components/`,
  `hooks/`, `lib/`, `i18n/`; `proxy.ts` guards signed-in routes).
- `server/` is the Express TypeScript API (entry `server/src/app.ts`). It is
  mounted on Vercel as one serverless function through `api/index.ts` and the
  `vercel.json` rewrites, and locally listens on the `.env` `PORT` (`4607` by
  default).
- `interview-agent/` is a separate, long-running LiveKit voice worker with its
  own package, environment and build. It is not a Vercel function. `extension/`
  is the browser extension, also its own package.
- Prisma's source schema is the multi-file folder `server/prisma/schema/`
  (`legacy.prisma` holds models inherited from RoboHire; `ra-*.prisma` hold one
  area each). The generated client under `server/src/generated/prisma/` is
  generated output; do not hand-edit it. RoboApply has its own Neon database.
- Production browser requests use same-origin `/api/*` paths. In development,
  `next.config.mjs` rewrites them to `NEXT_PUBLIC_API_URL`.

## Big picture

- **Two brands, one codebase.** RoboApply (`roboapply.io`, international and
  Taiwan, Stripe) and GoApply (`goapply.top`, mainland China, Alipay) are
  resolved per request from the Host header (`server/src/platform/brand/`; the
  frontend mirror is generated by `npm run gen:brand`). They have the same
  features; a `CN_<NAME>` variable is an optional override of `<NAME>`, never a
  gate. `ALLOWED_BRANDS` narrows what a deployment serves (production:
  `roboapply`). Capability flags live in `server/src/platform/flags.ts`.
- **Owner rulings bind every change** (`docs/jobright-clone/README.md`): D1 the
  product never submits an application for the user; D3 never fabricate data,
  sources, prices or counts; D5 brand parity; D6 sources, prices and payment
  rails are per market.
- **Server layout.** Feature modules live in `server/src/features/<area>/`;
  the older candidate API is `server/src/roboapply/` (legacy and V2 routers and
  agents); mock interviews are `server/src/interview-engine/` (practice prep
  agents and skills in `prep/` and `skills/`); cross-cutting services (brand,
  billing rails, residency, LLM policy, embeddings, startup checks) are in
  `server/src/platform/`; `server/src/cron/handlers.ts` serves the Vercel
  crons, which require `CRON_SECRET`.
- **LLM calls** go through `LLMService` (`server/src/services/llm/`). A task's
  model comes from the admin `AppConfig` row `llm_stack.{env}` when set (it
  overrides env on warm instances), else from env (`LLM_MODEL`,
  `LLM_<TASK>_MODEL`). `google/<model>` routes to Google directly,
  `openrouter/<vendor>/<model>` through OpenRouter. The Assistant (`copilot`
  task) needs a provider that streams tool calls (not Google direct or
  Anthropic); otherwise the production API refuses to boot
  (`server/src/platform/startup.ts`). Thinking models spend output tokens on
  reasoning, so agents with small caps need headroom.
- **Configuration layers:** env vars, then admin `AppConfig` overrides, then
  capability flags. Startup assertions stop the API on a fatal misconfiguration.

## Working rules

- Preserve existing user changes and keep edits narrowly scoped to the task.
  Several sessions may edit this checkout at once: stage explicit paths.
- Never commit `.env`, `.env.local`, credentials, tokens, or copied production
  data. Use `.env.example` when documenting configuration.
- The main checkout's `.env` points at the production database, may hold a live
  Stripe key, and a local API runs the platform crons in process unless
  `ROBOAPPLY_CRON_DISABLED=true`. Check which database you are on before any
  database command, and never let a test or command call a paid provider.
- Keep frontend API access behind modules in `lib/api/`; do not scatter raw API
  URLs through components (`npm run check:api-boundary` enforces it).
- Keep Express route handlers thin and put reusable business logic in the
  corresponding server service or library module.
- Maintain the existing ESM conventions and `.js` suffixes in relative imports
  from server TypeScript source.
- When changing authentication, keep the frontend and backend session-cookie
  constants aligned and verify both login and `/auth/me` behavior.
- When changing user-facing copy, update every supported locale (en, zh,
  zh-TW, ja, ko, es, fr, pt, de) and run the repository's copy checks. Use the
  `i18n-locale-sync` skill for locale work.
- Schema changes are additive only (no drops or renames); there is no
  migrations folder. The Alipay path and its tests are frozen.
- Read `docs/interview-practice/PREP_AGENTS.md` before changing
  `server/src/interview-engine/prep/`, `server/src/interview-engine/skills/` or
  the `/practice` setup. The two-brand build record, and the owner items still
  open, are in `docs/jobright-clone/HANDOFF.md` (its §2 predates the merge).

## Common commands

```bash
npm run dev                 # Express + readiness-gated Next (:3611) + voice-worker supervisor
npm run dev:server          # Express API only
npm run dev:web             # Next frontend only, port 3611
./scripts/dev-clone.sh      # Both brands: localhost:3621 and goapply.localhost:3621
npm test                    # Full root Vitest suite (web and server)
npx vitest run path/to/file.test.ts         # One test file
npx vitest run path/to/file.test.ts -t name # One test by name
npm run typecheck:server    # Express TypeScript check
npm run typecheck:web       # Next TypeScript check
npm run check               # Design, copy, LLM cost, API boundary, extension, zh-variant checks
npm run gen:brand           # Regenerate the frontend brand mirror (must leave no diff)
npm run eval:match -- --enforce M4          # Fit-ranking regression harness
npm --prefix extension test                 # Extension tests (not in root npm test)
npm --prefix interview-agent test           # Voice worker tests (not in root npm test)
npm run build               # Prisma generate + server build + Next production build
npm run db:generate         # Regenerate Prisma client after schema changes
```

Use Node 24.x and the committed `package-lock.json`; install dependencies with
`npm install` unless the task explicitly requires a lockfile refresh. `npm run
lint` is not usable (Next 16 removed `next lint`). CI (`.github/workflows/ci.yml`)
runs both typechecks, `npm test` and `npm run check` for the root, and the
extension and interview-agent suites separately.

## Verification

- Run the smallest relevant test first, then the full affected suite.
- Frontend or shared changes: run `npm test` and the applicable `npm run check`
  commands.
- Server changes: run `npm run typecheck:server` and relevant server tests.
- Schema changes: run `npm run db:generate`, then server type-check/tests. Do
  not run `db:push` against an unknown database.
- Deployment-affecting changes: run `npm run build` when it is safe to do so.
  Avoid running a Next production build against the same `.next` directory as
  an active `next dev` process. After a production deploy, check an
  `/api/v1/*` route: `/api/health` is served by Next and stays up when the API
  does not boot.
